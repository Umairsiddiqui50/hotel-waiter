### 2. MIGRATION PLAN: refresh_token columns on staff_users

**Required schema change: Add 2 columns to existing `staff_users` table**

**Why `staff_users` columns vs separate `staff_sessions` table:**
- `staff_users` columns: Simpler, one refresh token per staff user (supports single-session rotation model), no new table, leverages existing bcrypt infrastructure. Fits "work efficiently" principle.
- `staff_sessions` table: Multiple sessions per user, more granular revocation, but over-engineering for initial phase, additional migration complexity.

**Selected design: Add columns to `staff_users`**
- `refresh_token_hash` VARCHAR(255) - bcrypt hash of the refresh token JWT (nullable)
- `refresh_token_expires` DATETIME(timezone) - refresh token expiry time (nullable)
- Rationale: Refresh-token rotation (invalidate old, issue new) naturally supports single-active-token-per-user model. Revocation (logout, deactivation) clears the hash. Reuse rejection compares submitted hash against stored hash.
